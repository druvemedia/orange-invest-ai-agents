# Evaluation dataset

Ten synthetic, labelled incidents for comparing the multi-agent system with the single-agent baseline.
Everything is invented.

```
data/eval/
  cases/EVAL-NN/      investigation INPUTS only (what the tools and models may see)
    incident.json     the incident report given to both approaches
    conditions.json   simulated tool faults, applied identically to both approaches; never shown to a model
    logs.jsonl, metrics.jsonl, changes.jsonl, coverage_gaps.jsonl     this case's evidence
    dependencies.jsonl, historical_incidents.jsonl                    shared topology and history (copied from data/fixtures)
  labels.jsonl        GOLD LABELS: read only by the scorer, after all runs finish
```

The files are generated by `app/evaluation/dataset_builder.py` (`python -m app.evaluation.dataset_builder`), and
`tests/test_eval_dataset.py` checks that the committed files match it byte for byte. The case files use exactly
the same format as `data/fixtures`, so the five existing tools read them unchanged via `FixtureStore(case_dir)`.
Metric jitter is fixed (not random), and percentages are clamped to 0–100. Before Phase 6, EVAL-01's pool
utilisation reached an impossible 102%.

## Label format

| Field | Meaning |
|---|---|
| `expected_outcome` | `root_cause` or `inconclusive` |
| `root_cause` | `label_id`, `summary`, `match_all` (keyword groups; a hypothesis matches if every group has a term in its title or assessment) and `key_evidence` (record matchers that directly show the cause) |
| `acceptable_alternatives` | other root causes that count as correct |
| `inconclusive_acceptable` | whether "inconclusive" is acceptable for a case that has a root cause |
| `distractors` | tempting wrong explanations, used for the "distractor ranked first" metric |
| `must_consider` | hypotheses a good investigation should at least list |
| `rationale` | why the label is what it is |

## Cases

| Case | Scenarios | Gold root cause | Alternatives | Inconclusive OK? | Why |
|---|---|---|---|---|---|
| EVAL-01 | config change precedes incident | payments-api DB pool cut 40 → 8 (CHG-E01-2) | – | No | Change 5 min before onset, a log confirming it applied, pool at 100%, DB CPU flat: direct and consistent. |
| EVAL-02 | misleading deployment correlation | postgres-orders disk full | – | No | The report blames a deploy, but disk errors and the error rise start 17 min **before** it, and the deploy only changed an email template. |
| EVAL-03 | conflicting logs/metrics; config change | inventory batch-reservations flag rollout (lock contention) | lock contention in the inventory DB | No | Inventory's own error rate and health checks look fine; orders logs, DB lock waits and the flag timing agree. |
| EVAL-04 | missing/delayed metrics; dependency failure | external fraud-check slowdown | – | **Yes** | Logs show fraud-check timeouts and local resources are normal, but fraud-check metrics are missing. |
| EVAL-05 | dependency failure | email-provider returning HTTP 503 | – | No | Direct 503s from the provider; the only change is an unrelated frontend deploy. |
| EVAL-06 | retry/timeout problem | orders-service v6.1.0 retries without backoff (retry storm on inventory) | – | No | Inventory request rate ×5 while orders traffic is flat, right after the change. |
| EVAL-07 | **simulated tool failure** (metrics tool unavailable) | redis maxmemory cut to 2gb → OOM | – | **Yes** | The change record and OOM logs are direct, but a source failed. |
| EVAL-08 | multiple plausible hypotheses; missing metrics | payments pool reduction (CHG-E08-2) | fraud-check slowness + retry refactor | **Yes** | Two changes minutes apart and two failure signatures; fraud-check metrics missing. Both should be considered. |
| EVAL-09 | insufficient evidence | none: **inconclusive expected** | – | (expected) | No anomaly, no errors, no changes; frontend logs missing. Naming any cause is wrong. |
| EVAL-10 | strong hypothesis contradicted; misleading deploy | billing-batch's 200 workers exhausting DB connections | – | No | Errors persist after the deploy is rolled back; connections jump when the batch job starts. |

## Leakage controls

- Labels live outside every case directory. The tests check that no case file contains label text.
- Investigation code receives only `EvalCase.incident` and `EvalCase.tools()`. The runner loads labels only after
  every investigation has finished. A test checks this order, and another checks that no model request contains label text.
- Evidence naturally contains the facts that point to the cause (for example a "No space left on device" log). That is
  the point of an investigation, not leakage.
